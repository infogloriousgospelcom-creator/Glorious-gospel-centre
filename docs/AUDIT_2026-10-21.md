## 🔴 CRITICAL — Fix Before Going Live

### 1. Admin RBAC is broken — every role except `SUPER_ADMIN` is locked out of `/admin`

**Domain:** Security · **Files:** `services/auth.ts:71-74`, `supabase/migrations/0009_rls_policies.sql:77-81`, `0013_role_seeds.sql:26-52`

`getCurrentAdmin()` reads the caller's own admin row using the **user-scoped** client:

```ts
supabase.from("admins").select("role:roles(key)").eq("profile_id", userId).eq("is_active", true)
```

But the only policy on `public.admins` is:

```sql
create policy admins_admin_all on public.admins
  for all to authenticated
  using (public.has_permission('roles.manage'))
  with check (public.has_permission('roles.manage'));
```

`roles.manage` is granted **only** to `SUPER_ADMIN` (verified in `0013_role_seeds.sql:26-28`). `ADMIN`, `EDITOR`, `PRAYER_MINISTER` and `MEDIA_MANAGER` get explicit permission subsets that exclude it — so RLS hides *every* `admins` row from them, including their own. `roleKeys.length === 0` → `getCurrentAdmin()` returns `null` → `app/admin/(protected)/layout.tsx:12` redirects to `/admin/login`.

**Impact:** `FIRST_ADMIN.md:137-143` explicitly instructs the operator to add further admins with the `ADMIN` or `EDITOR` role. Doing so creates an account that authenticates successfully and is then **bounced straight back to `/admin/login` on every `/admin/*` URL**. The likely workaround an operator will apply under pressure is to hand the new user `SUPER_ADMIN`, collapsing the entire RBAC model the permission system was built for.

**Fix:** new migration granting self-read of one's own admin row + a `SECURITY DEFINER` role lookup that does not depend on RLS.

### 2. `gallery_items` has RLS enabled but **no policy** — the public gallery is silently empty

**Domain:** Security / Correctness · **Files:** `supabase/migrations/0009_rls_policies.sql:20`, `services/gallery.ts:92-119`, `services/content.ts:387-404`

`0009:20` enables RLS on `gallery_items`, but only creates policies for `gallery_albums` (`:207-216`). The comment at `0009:218` — *"Media + gallery items have no public table — access via storage policies"* — is **wrong**: gallery item rows are read through PostgREST, not storage.

Every read uses the anon/session client, so RLS applies and returns **zero rows**:

```ts
const { data, error } = await supabase.from("gallery_items").select(...)  // always empty
```

**Impact:** `app/gallery/[album]/page.tsx` renders albums with **no photos**, and `app/gallery/page.tsx` shows `item_count: 0` for every album. This is a **deny-all** (safe) failure mode, but it is a broken public feature. The naive fix (`grant select on gallery_items to anon`) would simultaneously expose `uploaded_by` — the fix must be a **policy with a column grant**.

### 3. Giving status override has **zero** server-side transition enforcement

**Domain:** Correctness · **File:** `services/admin/giving.actions.ts:52-68` (verified)

`lib/payment-transitions.ts` defines a correct state machine, but it is only consumed by the **callback** path. The staff override never calls it:

```ts
const { error } = await supabase
  .from("giving_transactions")
  .update({ status: parsed.data.status, admin_notes: parsed.data.reason })
  .eq("id", parsed.data.id);          // ← no canTransition(), no .neq("status","SUCCESS")
```

The docstring at `giving.actions.ts:32-36` claims *"Status transition rules / UI are unchanged"* — false. The UI (`StatusOverride.tsx:8-14`) offers all five statuses unconditionally.

**Impact:** Any account with `giving.manage` can flip a **real, received** transaction `SUCCESS → FAILED` (the gift vanishes from the books and from the donor's history), or `PENDING → SUCCESS` (a fabricated receipt shown to the donor). `SUCCESS → PENDING` is also allowed. Since migration `0033` revokes UPDATE from `authenticated`, this service-role write is the **only** gate.

### 5. Every "not found" page returns **HTTP 200** (soft 404s site-wide)

**Domain:** SEO / Correctness · **File:** `app/loading.tsx` (root) + `notFound()` callers

Verified against a production build:

```
/events/nope       → 200   (body contains "Page not found")
/sermons/nope      → 200
/gallery/nope      → 200
/connect/nope      → 200
/testimonies/nope  → 200
/not-a-real-route  → 404   ← unmatched routes are fine
```

**Root cause proven by isolation test** — an identical copy built with `app/loading.tsx` removed returns 404 for all of them. The root `app/loading.tsx` creates a Suspense boundary that flushes the response shell with **HTTP 200** before the page resolves; when `notFound()` then throws, Next sets `res.statusCode = 404` but the headers are already sent.

**Impact:** Google treats these as **soft 404s** — indexes them as thin duplicate pages, reports "Soft 404" in Search Console, and burns crawl budget on an infinite URL space (any `/ministries/<anything>` is reachable and returns 200).

### 9. M-Pesa transactions are never reaped — money can be taken and never recorded

**Domain:** Correctness · **Files:** `supabase/functions/mpesa-stk-push/index.ts:665-695`, `mpesa-callback/index.ts:309-334`

The only writers of `giving_transactions.status` are the STK-push function (`PENDING → PROCESSING|FAILED`) and the Daraja callback (`PROCESSING → SUCCESS|FAILED|CANCELLED`). There is **no timeout/reaper** anywhere — verified: zero `pg_cron` / `cron.schedule` / reaper references across all 38 migrations and the entire `services/` + `lib/` tree.

If the Daraja callback POST is lost (network partition, edge-function cold-start failure, malformed body → 400/500), the row stays `PROCESSING` **forever**. Daraja does not retry.

**Impact:** `services/member-giving.ts:80-89` filters nothing by age → the donor's "My Giving" list shows the gift as **"Processing" indefinitely** and the `warning` badge forever. The donor believes their money was lost. The admin's only recourse is the unguarded manual override (finding #3).

### 10. Stuck idempotency key + `UNIQUE(provider, external_reference)` can **permanently** block donations

**Domain:** Correctness · **Files:** `supabase/functions/mpesa-stk-push/index.ts:79-87, 560-615`, `supabase/migrations/0007_gallery_prayer_giving_contact.sql:84-86`

```ts
function generateIdempotencyKey(categoryId, amountCents, phone) {
  const bucket = Math.floor(Date.now() / (5 * 60 * 1000));
  return `${categoryId}|${amountCents}|${phone}|${bucket}`;   // created_by is NOT in the key
}
```

```sql
create unique index idx_giving_tx_external_ref
  on public.giving_transactions(provider, external_reference)
  where external_reference is not null;
```

The row is inserted with `external_reference = idempotencyKey` **before** the Daraja call. If the Daraja `fetch` throws, the outer `catch` returns 500 and **the row is never cleaned up**. The reuse query at `:560-574` only self-heals for the *same* user — for a **different user on the same phone number** (extremely common in Kenyan family/shared phones) the INSERT re-uses the identical key → **unique index violation** → HTTP 500 `"Could not initiate giving"`.

**Impact:** After any transient Daraja/network error, one member of a household permanently blocks every other member's gift of the **same amount to the same category**. The blockage is permanent.

**Secondary effect:** `services/giving.ts:220` looks up by `external_reference` with `.maybeSingle()`; when two rows share the reference, PostgREST errors, the lookup fails, and **a successful payment is silently never marked SUCCESS**.

## ✅ What the Codebase Already Does Well

Worth stating explicitly, because a lot of this is genuinely strong work:

- **Zero `any`, zero `as any`, zero `@ts-ignore`, zero `eslint-disable`** — strict TS discipline across the whole repo.
- **No IDOR in the member area** — every member read filters on `auth.uid()`; every member write re-derives ownership from the session. `ministry_serve_interests` has a BEFORE INSERT trigger that **overwrites** `new.profile_id := auth.uid()`.
- **JSON-LD `</script>` breakout correctly mitigated** — `lib/json-ld.ts:5-10` escapes `<`, `>`, `&` **after** `JSON.stringify` (the correct order), with a regression test.
- **Open redirect correctly mitigated** — `lib/auth-redirects.ts` blocks non-`/` paths, `//`, `\`, `@`, `://`, control chars; `safeMemberRedirect` blocks `/admin/*`; `safeAdminRedirect` allows **only** `/admin/*`.
- **No secrets in the client bundle** — `lib/env.ts` splits cleanly; `getServerEnv()` is imported only by `server-only` modules.
- **File upload validation is genuinely server-side** — magic-byte sniffing rejects SVG/HTML/executables (`lib/file-magic.ts:13-50`), with tests.
- **`timingSafeEqual` HMAC comparison** with a length pre-check; the callback **fails closed** when no secret is configured.
- **The payment state machine is correct where it IS applied** — `SUCCESS` is terminal and idempotently ignored, and the write carries a `.neq("status","SUCCESS")` guard against a lost race.
- **`redirect()` inside `try/catch` is correctly guarded everywhere** — every call re-throws the Next.js redirect error by `digest === "NEXT_REDIRECT"`.
- **`.maybeSingle()` used correctly** everywhere a table can legitimately have zero rows.
- **Honeypots + rate limits on every public intake form.**
- **`useFormStatus` wired correctly** — the submit button is a separate child component, so double-submit is blocked everywhere.
- **`focus-visible` rings, skip link, focus-trapped modals, `aria-expanded` accordions, `prefers-reduced-motion`** — all genuinely implemented and verified.
- **CI runs lint + typecheck + test + build** on every push.
